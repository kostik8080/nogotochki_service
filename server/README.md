# Сервер «Ноготочки»

Node.js 24.7+ и TypeScript, база SQLite через встроенный модуль `node:sqlite`, HTTP — встроенный `node:http`. Схема базы — `docs/db-schema.md`, как она устроена в коде и правила ее изменения — `docs/database.md`, эндпоинты API — `docs/api.md`.

## Первый запуск

```bash
cd server
npm install
cp .env.example .env     # заполнить SEED_ADMIN_PASSWORD, SEED_MASTER_PASSWORD и SEED_CLIENT_PASSWORD
npm run db:reset         # создать базу data/nogotochki.db с тестовыми данными
npm start                # API на http://localhost:3000
```

## Миграции

Файлы `src/db/migrations/NNN_description.sql` применяются по порядку номеров, каждый один раз. Примененную миграцию не правят (сервер это заметит по контрольной сумме): изменение схемы — новый файл со следующим номером.

Изменить `CHECK`, внешний ключ или тип поля в SQLite можно только пересозданием таблицы. Такая миграция начинается строкой `-- migrator: foreign_keys=off`: мигратор выключает проверку внешних ключей на время миграции и проверяет все ссылки перед фиксацией. Пример — `003_master_role.sql`.

## Выкладка на сервер

На сервере нужен только Node.js 24.7 или новее (рекомендуется последняя 24.x — ветка с долгосрочной поддержкой). Больше ничего: база работает через встроенный модуль `node:sqlite`, HTTP — через `node:http`, а хеширование паролей — через встроенный `node:crypto`, поэтому у сборки нет зависимостей и нативных модулей, которые пришлось бы компилировать на хостинге. Проверить версию: `node -v`.

Версию проверяют сами команды. `npm ci` и `npm install` на неподходящем Node откажутся работать (`engine-strict` в `.npmrc`), а все `npm run …` перед запуском подключают `scripts/node-version.mjs`: при старой версии он выводит, какая нужна и какая установлена, и останавливает команду. Требуемая версия задается в одном месте — `engines` в `package.json`.

Версию 24.7 задают две возможности Node: `argon2` в `node:crypto` (появился в 24.7) и `node:sqlite` без флагов. В ранних выпусках 24.x при запуске может печататься `ExperimentalWarning` про SQLite — это предупреждение, а не ошибка.

В окружении production обязательно:

* `NODE_ENV=production`;
* `DATABASE_PATH` — абсолютный путь вне папки с кодом, например `/var/lib/nogotochki/nogotochki.db`. Папку с кодом заменяют при обновлении, база внутри нее пропала бы.
* `BACKUP_DIR` — папка резервных копий: абсолютный путь вне папки с кодом и не та же, что у базы, например `/var/backups/nogotochki`.
* `UPLOADS_DIR` — папка фото работ, тоже вне папки с кодом, например `/var/lib/nogotochki/uploads`. Ее нужно копировать вместе с базой: в базе только пути к файлам.
* `APP_URL` — адрес сайта с `https://`: из него строятся ссылки в письмах.
* `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM` — почта для ссылок сброса пароля и кодов. Без нее восстановление пароля не работает.

**Весь сайт отдает сам сервер**, отдельный статический сервер не нужен. Клиентские страницы и файлы `css/`, `js/`, `img/` он берет из `WEB_DIR` (по умолчанию `../web` рядом с папкой `server/`) — `src/web/static-files.ts`. Страницы разделов сотрудников `/admin` и `/master` отдает `src/web/admin-pages.ts` после проверки роли по сессии: гостя уводит на вход, чужой роли отвечает 403. Файлами из `web/admin/` и `web/master/` эти страницы не отдаются никогда — иначе разметку раздела можно было бы открыть мимо проверки прав; это закреплено тестом `test/static-files.test.ts`.

Прокси перед сервером нужен только для HTTPS и передает ему все адреса целиком, без отдельных правил для статики.

API отдает cookie сессии с флагом `Secure`, поэтому в production он работает только за HTTPS (прокси хостинга или nginx). Если прокси передает IP клиента в `X-Forwarded-For`, задайте `TRUST_PROXY=1` — иначе ограничение частоты запросов будет считать всех клиентов одним.

Переменные удобно держать в файле `server/.env` на сервере: команды читают его сами, в том числе при запуске по расписанию. В git этот файл не попадает.

С неверными настройками команды не запускаются и пишут, что исправить. Тестовые данные в production не загружаются.

Первая выкладка:

```bash
npm ci                    # точные версии из package-lock.json
npm run build
npm prune --omit=dev      # убрать TypeScript и tsx, они нужны только для сборки
npm run prod:admin:create # учетная запись владельца студии
npm run prod:start        # API; держать запущенным — через менеджер процессов хостинга
```

Отдельно применять миграции не нужно: сервер при запуске сам создает папку базы, если ее нет, и применяет миграции, которых в базе еще нет, — до того как начнет отвечать (`src/db/auto-migrate.ts`). Уже примененные второй раз не применяются. Команда `npm run prod:migrate` осталась для случая, когда схему нужно обновить, не запуская сервер; она делает ровно то же самое.

Новая база стартует в режиме технических работ (`settings.is_maintenance = 1`): адрес и телефон в ней взяты из прототипа. Администратор вносит настоящие контакты и выключает режим в настройках студии (`PATCH /api/admin/settings` с `address`, `phone` и `isMaintenance: false`, см. `docs/api.md`) — тогда клиенты видят запись. Каталога в новой базе тоже нет: администратор заводит категории (`POST /api/admin/service-categories`), услуги, мастеров и их график через API.

Обновление — те же `npm ci`, `npm run build`, `npm prune --omit=dev` и перезапуск: миграции применятся при старте. Каждая миграция выполняется в своей транзакции: если она упадет, база останется прежней. Если миграция прошла, но сделала не то, поможет копия `…-pre-migrate.db`, которую `prod:migrate` делает перед применением.

## Запуск в контейнере

Контейнер собирается заново при каждом обновлении, и все, что лежало внутри, пропадает. Поэтому данные вынесены из образа в папку `/data`, которая подключается при запуске: база (`/data/db`), резервные копии (`/data/backups`) и фото работ (`/data/uploads`). Папки создаются сами при первом обращении, поэтому на чистом сервере ничего готовить не нужно.

Проще всего — одним описанием `docker-compose.yml` из корня проекта: в нем уже записаны том для данных, порт, адрес сервиса и первый администратор.

```bash
docker compose up -d --build   # запустить или обновить
docker compose logs -f         # журнал: в нем пароль первого администратора
docker compose down            # остановить; данные остаются в томе
```

Пароля в этом описании нет: пароль почты задается в панели сервера или в файле `.env` рядом с описанием (в репозиторий он не попадает), а пароль администратора сервер придумывает сам.

То же самое вручную:

```bash
docker build -t nogotochki .                 # из корня проекта: образу нужны и server/, и web/
docker run -d --name nogotochki -p 3000:3000 \
  -v /var/lib/nogotochki:/data \
  -e APP_URL=https://topbrohuman.ru \
  -e SMTP_HOST=… -e SMTP_USER=… -e SMTP_PASSWORD=… -e 'MAIL_FROM=Ноготочки <noreply@…>' \
  nogotochki
```

Что внутри: образ `node:24.19.0-alpine` (та же версия, на которой проект разрабатывается), только собранный `dist/` и файлы интерфейса из `web/` — зависимостей у сервера нет. Контейнер отдает и API, и сайт: после запуска по адресу сервера открывается лендинг, а не только `/api`. Контейнер работает не под `root`, а под пользователем `node` (uid 1000), поэтому папка с хоста должна быть ему доступна: `chown -R 1000:1000 /var/lib/nogotochki`. `docker stop` доходит до сервера сигналом `SIGTERM`, и тот закрывает соединения и базу сам.

Что в образ не копируется, перечислено в `.dockerignore`: локальная база и ее копии, `.env`, установленные зависимости, история git, прототип, черновой интерфейс и документация. Локальная база исключена намеренно — иначе она затерла бы настоящую на сервере.

### Каталог студии

Новая база пустая: без категорий, услуг и мастеров клиенты записи не увидят. Завести их можно в разделе администратора (`/admin/services`, `/admin/masters`) или одной командой — она заполняет тот же каталог, что виден при разработке: 4 категории, 14 услуг, правила опции «Дизайн ногтей», несовместимые услуги и 3 мастеров с недельным графиком.

```bash
docker compose exec app node --import ./scripts/node-version.mjs dist/scripts/setup-catalog.js
```

Вне контейнера — `npm run setup:catalog` (на сервере из сборки: `npm run prod:setup:catalog`).

В отличие от тестовых данных (`npm run db:seed`, в production не работает), команда не заводит ни учетных записей, ни клиентов, ни записей, ни фото — на работающем сервере им не место. Повторный запуск ничего не добавляет и не возвращает цены, которые администратор поправил в панели. Режим технических работ команда не трогает: его студия выключает сама, когда готова принимать клиентов. Данные каталога — `src/db/catalog.ts`, тесты — `test/catalog-setup.test.ts`.

### Первый администратор

Роль назначается только в базе, поэтому на новом сервере нужна учетная запись администратора — иначе некому завести услуги, мастеров и расписание.

Сервер заводит ее сам при запуске, если администраторов в базе еще нет и задан `ADMIN_EMAIL` (в `docker-compose.yml` он задан). Пароль берется из `ADMIN_PASSWORD`, а если его нет — придумывается случайным и один раз печатается в журнал:

```
Создана учетная запись администратора: admin@topbrohuman.ru
Пароль (показывается один раз, смените его в профиле после входа): …
```

Пароль нигде не хранится: после входа смените его в профиле (вкладка «Безопасность»). Повторный запуск, перезапуск контейнера и обновление ничего не меняют — учетная запись создается только когда администраторов нет вовсе, поэтому пароль владельца не сбрасывается (`src/db/bootstrap-admin.ts`, тесты — `test/bootstrap-admin.test.ts`).

Завести администратора руками, с выбором пароля, по-прежнему можно командой:

```bash
docker compose exec app node --import ./scripts/node-version.mjs dist/scripts/admin-create.js
```

## Резервные копии

`npm run prod:backup` делает копию базы командой SQLite `VACUUM INTO`. Копия целостная, даже если в это время сервер пишет в базу, и ее не нужно останавливать. Каждая копия сразу проверяется (`PRAGMA integrity_check`) и сохраняется одним файлом `nogotochki-ГГГГММДД-ЧЧММССZ.db` (время в UTC). Хранятся последние `BACKUP_KEEP` копий, по умолчанию 14, включая копии перед миграциями; другие файлы в папке команда не трогает.

**Расписание.** Копию нужно делать каждый день — в панели BeGet в разделе CRON. Пример на 03:00:

```
0 3 * * * cd /путь/к/проекту/server && /полный/путь/к/node --import ./scripts/node-version.mjs dist/scripts/db-backup.js >> /путь/к/логам/backup.log 2>&1
```

Путь к node указывается полностью (узнать: `which node`): у заданий cron свой, урезанный PATH, и просто `node` там может не найтись или оказаться старой версией. Раз в несколько дней стоит заглянуть в `backup.log`: при ошибке команда пишет ее туда и не создает копию.

**Копия вне сервера.** Копии в `BACKUP_DIR` лежат на том же сервере, что и база, и пропадут вместе с ним. Регулярно скачивайте свежую копию к себе или в облачное хранилище и проверьте, какие резервные копии аккаунта делает сам BeGet.

**Восстановление:**

1. Остановите сервер, чтобы он не писал в базу во время замены.
2. Отложите текущую базу, даже поврежденную, — вместе с файлами `-wal` и `-shm` рядом с ней, если они есть: `mv nogotochki.db nogotochki.db.broken` и так же для `nogotochki.db-wal`, `nogotochki.db-shm`. Старый `-wal` рядом с восстановленной базой испортил бы ее.
3. Скопируйте нужную копию на место базы: `cp /var/backups/nogotochki/nogotochki-….db /var/lib/nogotochki/nogotochki.db`.
4. Выполните `npm run prod:migrate`: если код новее копии, он применит недостающие миграции.
5. Запустите сервер.

Все, что было записано в базу после создания копии, при восстановлении теряется. Поэтому перед восстановлением из ежедневной копии проверьте, нет ли более свежей — например, копии перед миграциями.
