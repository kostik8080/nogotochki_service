# API «Ноготочки. Онлайн-запись»

REST API поверх базы из [`docs/db-schema.md`](db-schema.md). Код — `server/src/app.ts` и `server/src/api/`, тесты — `server/test/api.test.ts`. Запуск: `cd server && npm start` (порт `PORT`, по умолчанию 3000).

## Общие правила

| Что | Правило |
|---|---|
| Формат | Запросы и ответы — JSON. Тело запроса отправляется с `Content-Type: application/json`, иначе 415. |
| Время | Моменты времени — только UTC, ISO 8601 с `Z`: `2026-09-24T07:00:00.000Z`. Смещение пояса (`+03:00`) не принимается — 400. В ответах время тоже в UTC; в часовой пояс студии (`timezone` в ответе, `Europe/Moscow`) его переводит интерфейс при показе. Календарная дата студии — `YYYY-MM-DD` (параметр `date`). |
| Деньги | Целые копейки, поля `…Kop`: `180000` — это 1800 ₽. |
| Вход | Серверная сессия в cookie `nogotochki_session` (HttpOnly, SameSite=Lax, Secure в production). В базе — только хеш токена. Срок действия: клиенту 30 дней, администратору и мастеру 7; после него — 401 `SESSION_EXPIRED`. Активность срок не продлевает. |
| Ошибки | `{ "error": { "code": "SLOT_TAKEN", "message": "…", "details": … } }`. `code` — постоянный код для интерфейса, `message` — текст для человека. |
| Лишние поля | Неизвестное поле в теле или строке запроса — ошибка 400: опечатка не должна молча игнорироваться. |

**Коды ответа:**

| Код | Когда |
|---|---|
| 200, 201, 204 | Успех; 201 — создано, 204 — без тела |
| 400 | Неверные данные: формат, обязательные поля, несовместимые услуги, мастер не выполняет услугу. Для ошибок формы — `VALIDATION_ERROR` со списком `details.fields: [{ field, message }]` |
| 401 | Нет входа (`UNAUTHORIZED`), сессия истекла (`SESSION_EXPIRED`), неверный логин или пароль (`INVALID_CREDENTIALS`) |
| 403 | Не хватает прав: раздел администратора, чужая запись, правило 24 часов (`CHANGE_DEADLINE_PASSED`), доступ закрыт администратором (`ACCOUNT_BLOCKED`) |
| 404 | Нет такой записи, мастера, услуги или адреса |
| 409 | Конфликт: время занято (`SLOT_TAKEN`, в `details.alternatives` — до 8 ближайших свободных слотов этого мастера: сначала в тот же день ближе к выбранному времени, затем в следующие дни, до двух недель вперед; текст ошибки базы наружу не попадает), бронь истекла или не найдена, e-mail или телефон заняты, запись изменена другим сотрудником (`VERSION_CONFLICT`), запись уже отменена (`BOOKING_NOT_ACTIVE`) |
| 413, 415 | Слишком большое тело запроса; тело не JSON или файл не изображение |
| 429 | Слишком много запросов, неверных паролей подряд или повторный код раньше чем через минуту; заголовок `Retry-After` |
| 503 | Режим технических работ (`MAINTENANCE`); почта не настроена или не отвечает (`EMAIL_UNAVAILABLE`, `DELIVERY_FAILED`) |

**Роли.** Клиент видит и меняет только свои записи. Администратор — все, без правила 24 часов и без ограничений «2 часа до визита» и «90 дней вперед». Мастер видит только свое расписание (`GET /api/master/schedule`) и карточки записей из него (`GET /api/bookings/:id`); создание, перенос и отмена записи отвечают ему 403 `MASTER_NO_BOOKING_RIGHTS`. Эти действия для всех ролей выполняют одни и те же функции сервера (`server/src/booking/booking-service.ts`), различаются только права внутри них.

**Роли — список.** Сессия и ответы о пользователе содержат `roles` — список ролей учетной записи, и права везде проверяются наличием роли в нем (`hasRole` в `server/src/auth/sessions.ts`), а не равенством. В базе у учетной записи одна роль (`users.role`, решение заказчика — [db-schema.md](db-schema.md), «Роль одна, а не список»), поэтому сейчас в списке одно значение. Роль назначается только в базе (`npm run admin:create`, тестовые данные): поля `role` и `roles` API не принимает ни при регистрации, ни в профиле — 400.

**Три проверки на каждом эндпоинте.** Роль берется из базы (`sessions` → `users`), а не из запроса: поля, заголовки и параметры с ролью сервер не читает. Обработчик по порядку проверяет вход (401 `UNAUTHORIZED` или `SESSION_EXPIRED`), роль (403) и принадлежность запрошенного объекта (403) — `requireUser`, `requireRole` и `requireBookingAccess` / `requireMasterProfile` в `server/src/api/guards.ts`. Третья проверка обязательна и там, где роль уже совпала: клиент с правильной ролью не должен открыть чужую запись.

**Раздел администратора — одна проверка на весь раздел.** Роль администратора для всех `/api/admin/*` проверяет одна функция `requireAdmin` (`server/src/api/guards.ts`); ее вызывает `server/src/app.ts` до поиска маршрута. Обработчики раздела роль не проверяют, поэтому новый эндпоинт под `/api/admin` получает ту же защиту сам. Гостю — 401, клиенту и мастеру — 403, в том числе на несуществующий адрес раздела: по ответу нельзя узнать, какие адреса там есть. Тест `server/test/admin-access.test.ts` перебирает все маршруты раздела и падает, если хоть один ответит клиенту не 403. Эндпоинты администратора вне `/api/admin` — только `POST /api/bookings/:id/status`: права проверяет `setVisitResult` в `booking-service.ts`. Публичны намеренно только витрина и расчет слотов: `GET /api/studio`, `/api/services`, `/api/masters`, `/api/masters/:id`, `/api/masters/:id/slots`, `/api/slots`, `/api/studio/days`, `/api/gallery`, `/api/photos/:id/file`.

## Эндпоинты

### Вход

| Метод и адрес | Кто | Что делает |
|---|---|---|
| `POST /api/auth/register` | все | Регистрация клиента: `name`, `phone` и/или `email`, `password` (8–128 символов), `pdConsent: true`, `marketingConsent`. Пароль сразу хешируется argon2id; сохраняется дата и редакция согласия (`PD_POLICY_VERSION`). Сразу открывает сессию. Занятый e-mail или телефон зарегистрированного клиента — 409. **Сценарий 16**: если номер есть в карточке клиента, которого записали по звонку, ответ 202 `phone_verification_required` — код приходит на e-mail из карточки клиентки (`delivery: email`, `sentTo` — адрес со скрытой частью), а если его там нет — код выдает администратор по звонку (`delivery: studio`). SMS в сервисе нет. Повторный запрос с теми же полями и `code` добавляет пароль к существующей карточке (201, `linkedExistingClient: true`): второй клиент не создается, прежние записи сразу в кабинете. Без кода привязки нет |
| `POST /api/auth/login` | все | Вход по телефону или e-mail (`login`) и паролю, один для всех ролей. После 5 неверных паролей подряд вход закрыт на 15 минут (429) |
| `POST /api/auth/logout` | все | Закрывает сессию и снимает бронь времени пользователя, чтобы слот освободился сразу |
| `GET /api/auth/me` | вошедший | Своя учетная запись: имя, `roles` — список ролей, телефон, e-mail, подтверждены ли они. Без хеша пароля и служебных полей. Поле `role` оставлено для чернового интерфейса `web-draft/`; `web/` проверяет `roles`. То же `user` — в ответе `POST /api/auth/login` и регистрации |
| `POST /api/auth/password-reset/request` | все | Восстановление пароля по `login`. На e-mail аккаунта приходит одноразовая ссылка `APP_URL/reset-password?token=…` (60 минут) — и при входе по телефону. Если в аккаунте нет e-mail, код из 6 цифр выдает администратор по звонку (`POST /api/admin/users/:id/password-reset-code`). Ответ всегда 202 — одинаковый, есть такой аккаунт или нет. Не чаще раза в минуту на аккаунт |
| `POST /api/auth/password-reset/confirm` | все | Новый пароль: `{ token, password }` по ссылке или `{ login, code, password }` по коду от администратора. Код перестает действовать после 3 неверных попыток. Все сессии пользователя закрываются; адрес, на который пришла ссылка или код, считается подтвержденным |

### Профиль

| Метод и адрес | Кто | Что делает |
|---|---|---|
| `PATCH /api/profile` | вошедший | Имя и согласие на новости (`name`, `marketingConsent`) |
| `POST /api/profile/password` | вошедший | Смена пароля: `currentPassword`, `newPassword`. Неверный текущий пароль — 403. Остальные сессии закрываются, текущая остается |
| `POST /api/profile/email` | вошедший | Новый (или неподтвержденный) e-mail: на него уходит код. Адрес занят — 409 |
| `POST /api/profile/email/confirm` | вошедший | Ввод кода: адрес записывается в профиль и отмечается подтвержденным. До кода профиль не меняется |
| `POST /api/profile/phone` | вошедший | Запрос нового телефона (202, `delivery: studio`). SMS нет: человек звонит в студию, администратор убеждается, что это он, и диктует код (`POST /api/admin/users/:id/phone-code`). До кода номер в профиле не меняется |
| `POST /api/profile/phone/confirm` | вошедший | Ввод кода от администратора: номер записывается в профиль и отмечается подтвержденным |
| `DELETE /api/profile` | клиент | Удаление аккаунта с подтверждением паролем (`password`). Предстоящие записи отменяются, имя заменяется на «Удаленный клиент», телефон, e-mail, пароль, согласия, карточка, заметки, комментарии к записям, сессии и неопубликованные фото визитов стираются. Прошедшие визиты остаются в истории студии без связи с человеком (решение 20 схемы) |

### Студия, услуги, мастера

| Метод и адрес | Кто | Что делает |
|---|---|---|
| `GET /api/studio` | все | Название, адрес, телефон, ссылки, часовой пояс, режим работы и правила записи (шаг слотов, горизонт, 2 часа до визита, 24 часа на изменение, 10 минут брони), режим технических работ |
| `GET /api/studio/days?from=&to=` | все | Особые дни студии для календаря: закрытые дни и сокращенные часы с причиной («Санитарный день»). По умолчанию — от сегодня на горизонт записи |
| `GET /api/gallery?masterId=` | все | Галерея «Наши работы» или работы мастера: опубликованные фото с подписью, мастером и услугой |
| `GET /api/photos/:id/file` | все / администратор | Файл фото. Опубликованное доступно всем, неопубликованное — только администратору (остальным 404) |
| `GET /api/services` | все | Каталог: активные услуги по категориям с длительностью и ценами мастера и топ-мастера; к каким услугам можно добавить опцию; несовместимые пары с объяснением |
| `GET /api/masters?services=8,3:2` | все | Активные мастера. С `services` — только те, кто выполняет **все** услуги визита, и стоимость и длительность визита у каждого (цена зависит от уровня мастера). Формат `services`: номера услуг через запятую, количество — через двоеточие |
| `GET /api/masters/:id` | все | Профиль мастера: уровень, специализация, рассказ, услуги с ценой по его уровню |

### Свободное время

| Метод и адрес | Кто | Что делает |
|---|---|---|
| `GET /api/masters/:id/slots?date=…&services=…` | все | Свободное время мастера на дату студии для визита из этих услуг: `slots: [{ startsAt, endsAt }]` в UTC, режим дня (`open`, `studio_closed` с причиной, `master_off`), длительность и цена визита. Считается **при каждом запросе** из графика мастера (с изменениями на дату и режимом студии), созданных записей с уборкой после них, блокировок и чужих действующих броней; таблицы готовых слотов нет. Визит целиком помещается в рабочее время, уборка не задевает следующую запись |
| `GET /api/masters/:id/slots?date=…&bookingId=…` | владелец записи, администратор | То же для переноса: длительность и уборка берутся из записи, сама запись не считается занятым временем, цена пересчитывается только у мастера другого уровня |
| `GET /api/slots?date=…&services=…` | все | Вариант «Любой свободный мастер»: слоты всех подходящих мастеров, в каждом — `masterIds` свободных мастеров; список мастеров с ценой визита |

### Бронь времени

| Метод и адрес | Кто | Что делает |
|---|---|---|
| `POST /api/holds` | клиент, администратор | Закрепляет время на `slot_hold_min` минут (10) на время оформления. Тело: `startsAt` и `services` с `masterId` (или `masterId: null` — «Любой мастер», сервис назначит первого свободного), либо `bookingId` для переноса. В транзакции `BEGIN IMMEDIATE` удаляет истекшие брони и прежнюю бронь пользователя, заново проверяет время и создает бронь; одновременную вторую бронь на то же время база отклонит триггером. Занято — 409 с альтернативами. Ответ: мастер, цена, `expiresAt` и `secondsLeft` |
| `GET /api/holds/current` | клиент, администратор | Действующая бронь пользователя или `null`, если ее нет или она истекла |
| `DELETE /api/holds/current` | клиент, администратор | Снять бронь («Выйти из записи»): время освобождается сразу |

Истекшая бронь перестает мешать другим сразу по `expires_at`, а строки удаляются уборкой раз в минуту и при каждой новой брони.

### Уведомления клиента

Уведомление создается, только когда запись клиента изменил администратор: отменил, перенес или поставил на то же время второй визит (`server/src/notify/notifications.ts`). Свои действия клиент не получает. Писем и SMS об этих событиях нет — уведомление живет в кабинете.

| Метод и адрес | Кто | Что делает |
|---|---|---|
| `GET /api/notifications?unread=&limit=` | клиент | Свои уведомления, новые сверху, и число непрочитанных одним ответом: `{ unreadCount, notifications: [{ id, type, text, bookingId, isRead, createdAt }] }`. Отдельного запроса ради счетчика нет. `type` — `booking_cancelled`, `booking_rescheduled` или `booking_overbooked`; `text` приходит готовым, с конкретными датой и временем в часовом поясе студии; `bookingId` — запись, по которой открывается ее карточка. `unread=true` — только непрочитанные, `limit` — до 100 (по умолчанию 30) |
| `POST /api/notifications/:id/read` | владелец | «Прочитано»: клиент закрыл уведомление. В ответе новый `{ unreadCount }`. Повторный вызов ничего не меняет. Чужое уведомление — 404: по ответу нельзя узнать чужие номера |

### Записи

| Метод и адрес | Кто | Что делает |
|---|---|---|
| `POST /api/bookings` | клиент, администратор | Создает запись: `masterId`, `startsAt`, `services`, `comment`, `isAnyMaster`. Клиенту нужна его действующая бронь на то же время и услуги (иначе 409 `HOLD_NOT_FOUND`, `HOLD_EXPIRED`, `HOLD_MISMATCH`). Администратор записывает без брони клиента из базы (`clientId`) или нового клиента по имени и телефону (`newClient`). С `isOverbooking: true` администратор ставит запись поверх записи другого клиента или блокировки мастера — обеда, личного времени (осознанное наложение): рабочее время и чужие брони все равно проверяются, а для других записей она занимает время как обычная. От клиента поле принимается, но отбрасывается — запись создается обычной. В карточке у администратора — `isOverbooking`. Время проверяется повторно в транзакции, бронь снимается, название, цена и длительность услуг копируются в запись |
| `GET /api/bookings?status=…&period=upcoming\|past` | клиент | Свои записи: предстоящие сверху, затем прошедшие и отмененные. У каждой — услуги, мастер, сумма, отмена с причиной, `canChange` и `changeDeadline` по правилу 24 часов |
| `GET /api/bookings/:id` | владелец, мастер записи, администратор | Карточка записи. Три проверки: вход, роль, владение объектом. Чужая запись — 403 («Это чужая запись» клиенту, «Эта запись не из вашего расписания» мастеру). Мастер видит запись только из своего расписания (`masters.user_id`) и в ней состав, комментарий, имя клиента, его «Важно» и отметку о наложении — без цен, контактов и истории. Администратор дополнительно видит контакты клиента, время уборки, кто создал запись и историю изменений |
| `POST /api/bookings/:id/reschedule` | владелец, администратор | Перенос той же записи: `startsAt`, `masterId` (другой мастер), `reason`, `version`. Клиенту нужна бронь на перенос (`POST /api/holds` с `bookingId`) и не позднее чем за 24 часа до визита. Цена пересчитывается только у мастера другого уровня; старое и новое время, мастер и суммы попадают в историю. Администратор с `isOverbooking: true` переносит поверх записей других клиентов и блокировок; обычный перенос снимает отметку наложения. От клиента поле отбрасывается |
| `POST /api/bookings/:id/cancel` | владелец, администратор | Отмена: `reason`, `version`; администратор указывает `by: client \| studio`. Сначала событие отмены в журнале, затем статус. Клиент — не позднее чем за 24 часа (иначе 403 с телефоном студии). Отмена администратором создает клиенту уведомление; своя отмена — нет |
| `POST /api/bookings/:id/status` | администратор | «Визит завершен» или «Клиент не пришел»: `status: completed \| no_show`, `reason`, `version`. Только для визита, который уже начался (иначе 409 `VISIT_NOT_STARTED`); ошибочную отметку можно поменять на другую. Отмененную запись отметить нельзя. Каждая смена — событие в истории |
| `POST /api/bookings/:id/acknowledge` | владелец | Клиент закрыл баннер «Запись отменена или перенесена студией». Баннер виден в поле `studioChange` записи (`{ type, at }` или `null`) |

`version` — номер версии записи, который видел пользователь. Если запись уже изменил другой сотрудник, ответ 409 `VERSION_CONFLICT` (экран A-S1).

### Раздел администратора

| Метод и адрес | Что делает |
|---|---|
| `GET /api/admin/bookings` | Все записи студии с контактами клиентов. Фильтры: `dateFrom`, `dateTo` (даты студии, включительно), `masterId`, `serviceId`, `clientId`, `status`, `limit` (до 500), `offset`; в ответе `total` |
| `GET /api/admin/services` | Все услуги, включая отключенные: цены, длительность, уборка, мастера, правила опции; категории и несовместимые пары |
| `POST /api/admin/service-categories` | Новая категория (A-23, «+ Категория»): `name`, `sortOrder` (по умолчанию — в конец), `isActive`. Новая база стартует без категорий, а без них нельзя завести услугу |
| `PATCH /api/admin/service-categories/:id` | Переименовать, поменять порядок, отключить (`isActive: false` — категория и ее услуги пропадают из каталога). Название не повторяется без учета регистра. Удаления нет: на категорию ссылаются услуги |
| `POST /api/admin/services` | Новая услуга: `categoryId`, `kind` (`main` или `addon`), `name`, `durationMin`, `cleanupMin`, `priceMasterKop`, `priceTopKop`, `priceUnit`, `maxQuantity`, `isFeatured`, `sortOrder`, `isActive`, `masterIds`, `addonForServiceIds` (для опции). Проверки на сервере (400 `VALIDATION_ERROR`, поле — в `details.fields`): название не пустое, длительность от 1 минуты, обе цены больше нуля, цена топ-мастера не ниже цены мастера. Название не повторяется без учета регистра (409). Те же проверки — в `PATCH` |
| `PATCH /api/admin/services/:id` | Изменение услуги, включая `isActive: false` — отключение. Созданные записи сохраняют прежние название, цену и длительность: они скопированы в запись (`booking_items`) в момент оформления |
| `DELETE /api/admin/services/:id` | Удаление решает сервер. На услугу не ссылаются ни записи, ни фото работ — строка удаляется вместе с отметками мастеров, правилами опции и парами несовместимых услуг: 200 `{ result: 'deleted' }`. Ссылки есть — услуга только отключается: 200 `{ result: 'deactivated', message, bookingsCount, photosCount, service }`, в `message` — объяснение для администратора («У услуги есть записи (3), поэтому она отключена, а не удалена…»). 404 — услуги нет |
| `POST /api/admin/service-incompatibilities` | Пара несовместимых услуг `serviceIds: [a, b]` с объяснением для клиента |
| `DELETE /api/admin/service-incompatibilities/:a/:b` | Убрать пару |
| `GET /api/admin/masters` | Все мастера, включая отключенных: уровень, услуги, действующий и будущий недельный график |
| `POST /api/admin/masters` | Новый мастер: профиль, `level`, `serviceIds` и `schedule: { validFrom, days: [{ weekday, start, end }] }` |
| `PATCH /api/admin/masters/:id` | Изменение мастера, уровня, услуг (`serviceIds` заменяет список целиком); `isActive: false` — отключение, в ответе предстоящие записи мастера, которые нужно перенести или отменить. Имя не может быть пустым (400) |
| `DELETE /api/admin/masters/:id` | Удаление решает сервер. У мастера нет записей, фото работ, заметок о клиентах «со слов мастера» и учетной записи для входа — строка удаляется вместе с его услугами, графиком, сменами на даты и блокировками: 200 `{ result: 'deleted' }`. Иначе мастер только отключается: 200 `{ result: 'deactivated', message, bookingsCount, master, upcomingBookings }`. 404 — мастера нет |
| `POST /api/admin/masters/:id/account` | Учетная запись мастера для входа: `email` и/или `phone`, `password`. Мастер видит свое расписание и меняет пароль в профиле. Уже есть — 409 `MASTER_HAS_ACCOUNT`. В карточке мастера — `account` |
| `PUT /api/admin/masters/:id/schedule` | Новый недельный график с даты (сценарий 14): текущие строки закрываются днем накануне. В ответе — действующие записи с этой даты, которые в новый график не попадают. С `dryRun: true` график не сохраняется |

**Расписание.** Каждое изменение отвечает списком `affectedBookings` — действующих записей, которые оно задевает. База их не трогает: администратор переносит или отменяет их сам. С `dryRun: true` изменение не сохраняется, а только показывает этот список (предпросмотр до сохранения).

| Метод и адрес | Что делает |
|---|---|
| `GET /api/admin/time-blocks?masterId=&from=&to=` | Блокировки мастеров за период |
| `POST /api/admin/time-blocks` | Блокировка: `masterId`, `type` (`lunch`, `personal`, `day_off`, `vacation`, `sick_leave`, `other` — для него обязателен `comment`), `startsAt`, `endsAt` в UTC. Слоты на это время пропадают сразу (сценарий 8) |
| `DELETE /api/admin/time-blocks/:id` | Удалить блокировку |
| `GET /api/admin/masters/:id/days?from=&to=` | Изменения смены мастера на даты |
| `PUT /api/admin/masters/:id/days/:date` | Рабочий день вне графика (`isWorking: true`, `start`, `end`) или выходной (`isWorking: false`). Открыть день, когда закрыта студия, нельзя — студия важнее мастера |
| `DELETE /api/admin/masters/:id/days/:date` | Убрать изменение: день снова по недельному графику |
| `GET /api/admin/studio-days?from=&to=` | Особые дни студии с автором |
| `PUT /api/admin/studio-days/:date` | Особый день для всех мастеров: закрыта (`isOpen: false`) или особые часы (`isOpen: true`, `open`, `close`), `reason` видна клиентам. Прошедший день — 400 |
| `DELETE /api/admin/studio-days/:date` | Убрать особый день |

**Клиентская база.** Метки, статистика и любимый мастер считаются по записям при каждом запросе. Метки: «Новый» (`new`) — не больше одного завершенного визита; «Давно не приходил» (`lapsed`) — последний завершенный визит больше 90 дней назад; «Постоянный» (`regular`) — от 5 завершенных визитов. В паспорте и прототипе порогов нет, они заданы в `TAG_RULES` (`server/src/api/admin-clients.ts`).

| Метод и адрес | Что делает |
|---|---|
| `GET /api/admin/clients?search=&filter=&sort=&limit=&offset=` | Клиенты: имя, телефон, e-mail, есть ли аккаунт, число визитов, последний визит, сумма, любимый мастер, метка, черный список. Поиск по имени (без учета регистра, в том числе кириллицы), e-mail и цифрам телефона; `filter`: `new`, `regular`, `lapsed`, `blacklist`; `sort`: `name`, `lastVisit`, `visits` |

## Раздел мастера

Мастер смотрит свое расписание и подает заявки администратору. Расписание он не меняет: заявка вступает в силу, только когда ее одобрит администратор.

| Метод и адрес | Что делает |
|---|---|
| `GET /api/master/schedule?from=&to=` | Свое расписание, только чтение (до 31 дня, по умолчанию неделя с сегодняшнего дня): по дням — рабочее окно или причина закрытого дня, записи (время, услуги, комментарий, статус, отметка наложения, имя клиента и поле «Важно»), блокировки. Контактов клиентов и цен нет. Учетная запись не связана с профилем мастера — 403 `MASTER_NOT_LINKED` |

### Заявки мастера

Типы: `vacation` — отпуск, `day_off` — отгул, `sick_leave` — больничный (у всех трех период дат `startsOn`–`endsOn` включительно); `schedule` — новый недельный график (`validFrom` и `days: [{ weekday, start, end }]`); `other` — свободная просьба словами (обязателен `comment`). Состояния: `pending`, `approved`, `rejected`, `cancelled`.

| Метод и адрес | Кто | Что делает |
|---|---|---|
| `GET /api/master/requests` | мастер | Свои заявки, новые сверху: тип, период или график, состояние и решение администратора с причиной |
| `POST /api/master/requests` | мастер | Новая заявка — всегда за себя: номер мастера берется из его профиля, поле из запроса не принимается. 400 `DATE_IN_PAST` — дата уже прошла |
| `POST /api/master/requests/:id/cancel` | мастер | Отозвать свою заявку, пока она на рассмотрении. 409 `REQUEST_ALREADY_DECIDED` |
| `GET /api/admin/requests?status=&masterId=` | администратор | Все заявки и `pendingCount` — число нерассмотренных — одним ответом. Нерассмотренные идут первыми |
| `GET /api/admin/requests/:id/affected` | администратор | Записи, которые заденет одобрение: их показывают до решения |
| `POST /api/admin/requests/:id/approve` | администратор | Одобрить и применить сразу: отпуск, отгул и больничный создают блокировку времени, `schedule` — новый недельный график с даты (теми же функциями, что и ручные действия администратора). В ответе `affectedBookings` — записи, которые не помещаются в изменение: база их не трогает. `dryRun: true` — только показать их. 409 `REQUEST_ALREADY_DECIDED` |
| `POST /api/admin/requests/:id/reject` | администратор | Отклонить. `reason` обязательна — мастер видит ее в своих заявках. Расписание не меняется |

## Почта

Письма с кодами и ссылками отправляет встроенный SMTP-клиент (`server/src/notify/mailer.ts`, без зависимостей): порт 465 — TLS сразу, другие порты — STARTTLS; без шифрования соединяется только с сервером на этом же компьютере. Настройки — `SMTP_*` в `server/.env`. При разработке без SMTP письма печатаются в консоль сервера. В production без SMTP смена e-mail отвечает 503, ссылка для сброса пароля не уходит — тогда код выдает администратор.

**SMS в сервисе нет** (решение студии). Телефон подтверждает администратор: человек запрашивает подтверждение на сайте, звонит в студию, администратор убеждается, что это он, и диктует код. Так же выдается код для сброса пароля, если в аккаунте нет e-mail.

## Страницы раздела администратора

Страницы `/admin`, `/admin/services`, `/admin/masters` (файлы `web/admin/*.html`) отдает этот же сервер, а не статический: доступ к разделу решает сессия (`server/src/web/admin-pages.ts`). Доступ проверяет та же функция `requireAdmin`, что закрывает `/api/admin/*`.

| Кто | Ответ |
|---|---|
| Гость, сессия истекла | 302 на `/login.html?next=/admin…` — общую форму входа; после входа администратор возвращается на эту страницу |
| Клиент, мастер | 403, страница «Этот раздел только для администраторов» (`web/forbidden.html`) — на любой адрес под `/admin`, в том числе несуществующий |
| Администратор | 200 и страница; неизвестный адрес под `/admin` — 404 |

Методы — только `GET` и `HEAD` (иначе 405). Ответы не кэшируются: `Cache-Control: no-store`, `Vary: Cookie`. Файлы страниц сервер берет из `WEB_DIR` (по умолчанию `../web`).

## Чего в API пока нет

Все функции паспорта есть в API. Клиентский интерфейс сверстан в `web/` (экраны и их эндпоинты — [frontend-log.md](frontend-log.md)). Раздела мастера в настоящем интерфейсе еще нет, раздел администратора — пока каркас без данных (`/admin`); для них есть черновой фронтенд без дизайна — `web-draft/` (как запустить — `web-draft/README.md`).
