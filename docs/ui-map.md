# Карта экранов

Рабочий документ перед версткой клиентской части и раздела администратора. Для каждого экрана — файл прототипа, что экран показывает, какие эндпоинты дают ему данные, какие эндпоинты вызывают его кнопки и куда ведут переходы. В конце каждой части — два списка: экраны, которым API не дает нужного, и эндпоинты, которым не нашлось экрана.

Первая часть — экраны клиента и гостя, составлена 27.09.2026. Вторая — [раздел администратора](#раздел-администратора), добавлена 29.09.2026.

Первая часть составлена по трем источникам:

* прототип `Prototype/` — разметка и таблица маршрутов (`ROUTES` в скрипте прототипа);
* карта связей [`karta-svyazey-prototipa.xlsx`](karta-svyazey-prototipa.xlsx) — ID экранов (листы «Реестр», «Навигация», «Связи»). Карта сверена с прототипом 25.09.2026, еще до решения «без SMS»;
* код API `server/src/api/` и его описание [`api.md`](api.md).

**Решения студии, которые меняют прототип:**

* **SMS в проекте нет** — ни кодов, ни уведомлений, ни подтверждений. Все, что в прототипе связано с SMS, в верстку не переносится: вход по коду из SMS, «код отправлен на телефон».
* **Телефон не подтверждается** (решение 27.09.2026). Новый номер в профиле сохраняется сразу. Администратор кодов по звонку не диктует. Остается одно подтверждение — e-mail кодом из письма; через e-mail же идут сброс пароля и привязка прежних записей (сценарий 16). Если e-mail в аккаунте нет, администратор после звонка вносит его в карточку.

API пока работает по-старому: подтверждает телефон кодом от администратора и выдает коды сброса пароля по звонку. Бэкенд сейчас не меняем, все решается на стороне экрана: экраны не вызывают эти возможности API. Как именно — в списке 1 (пункты 9–13); что на экране не решить — в конце документа.

В первую часть входят только экраны клиента и гостя. Экраны администратора (`A-*`), вход сотрудника (`AUTH-04`) и «Учетная запись заблокирована» (`SYS-04`) — во второй части. Панель разработчика прототипа (`SYS-07`) и дизайн-система (`DS-01`) в карту не вошли.

## Как читать

* **Файл прототипа.** «Лендинг» — `Prototype/Лендинг - Ноготочки.dc.html`. «Прототип» — `Prototype/Прототип - Ноготочки.dc.html`; в нем все остальные экраны, адрес после `#` — маршрут экрана. У модалок своего адреса нет: указан экран, на котором они открываются.
* **Данные** — запросы `GET`, которые экран делает при открытии. **Кнопки** — запросы, которые меняют данные, и коды ответов, которые экран должен различать.
* **Переходы** — ID экранов из карты связей. `EXT` — внешняя ссылка (телефон, карта, соцсети). «Черновик записи» — выбранные услуги, мастер и время, которые хранит браузер (см. список 1, BOOK-04).
* Время в API — UTC, в часовой пояс студии (`timezone` из `GET /api/studio`) его переводит интерфейс. Деньги — копейки (`…Kop`).

## Общее для всех экранов

| Что | Откуда |
|---|---|
| Вошел ли человек и кто он (шапка, меню, редиректы) | `GET /api/auth/me`. Ответ 401 — гость. `role` не `client` — сотрудник, клиентские экраны ему не нужны |
| Название, адрес, телефон, ссылки на карту и соцсети, режим работы, правила записи, режим технических работ | `GET /api/studio` |
| Сессия истекла на любом экране | Ответ 401 `SESSION_EXPIRED` → вход (AUTH-01) с возвратом на тот же экран; в записи — модалка BOOK-M3 |
| Ошибки | `{ error: { code, message, details } }`. `message` можно показывать как есть; ошибки полей формы — `details.fields` |
| Выход | `POST /api/auth/logout` — закрывает сессию и снимает бронь |

## 1. Экраны, для которых в API не хватает данных

Правило решений: бэкенд сейчас не трогаем, все решается на стороне экрана. Варианты решения:

* это не данные, а обычный контент страницы;
* данные в API на самом деле есть — вот эндпоинт;
* можно собрать из нескольких запросов к существующим эндпоинтам;
* убрать элемент из верстки;
* значение брать из API, а текст на экране привести к нему.

| Находка | Решение | Почему |
|---|---|---|
| **1.1** PUB-01: дни работы мастера на карточке. Недельный график отдает только `GET /api/admin/masters` | **Убрать элемент из верстки** | Иначе — 7 запросов слотов на каждого мастера при загрузке лендинга, а актуальные дни клиент все равно увидит на шаге «Время» |
| **1.2** PUB-01: цифры полосы доверия | **Это обычный контент страницы** | Это рекламный текст студии, как «Как это работает»; цифры дает студия, а не база |
| **1.3** PUB-01: «Свободное время есть уже на этой неделе» | **Убрать элемент из верстки** | Это утверждение о данных: проверить его можно только перебором слотов, а ложное обещание на лендинге хуже, чем никакого |
| **1.4** PUB-01: отзывы | **Это обычный контент страницы** | Отзывы как функцию паспорт исключает, а цитаты, которые студия дала сама, — это текст лендинга. Нет настоящих цитат — блок не верстаем |
| **2** PUB-05, BOOK-02: плашка «в отпуске до …» | **Убрать элемент из верстки** | Блокировки мастеров видит только администратор, а отпуск и так виден клиенту: в эти дни нет свободного времени |
| **3** BOOK-02: «Ближайшее: …» у каждого мастера | **Можно собрать из нескольких запросов:** для каждого мастера `GET /api/masters/:id/slots?date=…&services=…`, начиная с сегодняшней даты студии, по одному дню, пока не найдется первый слот. Не дальше 14 дней, мастера — параллельно. Не нашлось — строку не показывать | Обычно время находится в первые 1–3 дня, то есть за 1–3 запроса на мастера, а подсказка помогает выбрать мастера |
| **4.1** BOOK-03, CAB-04: точки у дней со свободным временем в календаре на месяц | **Можно собрать из нескольких запросов:** на каждый день видимого месяца в пределах горизонта — `GET /api/masters/:id/slots` (для «Любого мастера» — `GET /api/slots`; при переносе — с `bookingId`). Дни, закрытые по режиму студии (`GET /api/studio`, `hours`) и особым дням (`GET /api/studio/days`), не запрашивать. Выходной мастера виден по `day.status` в ответе | Студия работает вт–сб, так что это около 22 запросов на месяц. Они же дают слоты выбранного дня без отдельного запроса |
| **4.2** BOOK-03: «Ближайшее свободное время» | **Можно собрать из нескольких запросов:** сначала дни уже загруженного месяца из 4.1, затем следующие дни по одному запросу, до горизонта `rules.bookingHorizonDays` из `GET /api/studio` | Первый свободный день почти всегда находится в уже загруженном месяце, дополнительных запросов нет |
| **4.3** BOOK-03, CAB-04: «На этот день мест нет» с ближайшими датами | **Можно собрать из нескольких запросов:** ближайшие 3 дня со слотами берутся из данных месяца (4.1) | Эти данные уже загружены для точек календаря |
| **4.4** BOOK-03: «В ближайшие 3 месяца все занято» | **Убрать элемент из верстки.** Вместо него — состояние месяца «В этом месяце свободного времени нет» из данных 4.1 и стрелка на следующий месяц | Проверить весь горизонт — до 90 запросов, а пустой месяц и так виден по календарю |
| **5** BOOK-03 «У вас запись в это время», BOOK-04 «У вас уже есть запись на это время» | **Можно собрать из нескольких запросов:** `GET /api/bookings?period=upcoming`. Слот, который пересекается с `[startsAt, endsAt)` действующей записи клиента, помечать; на BOOK-04 показывать предупреждение со ссылкой на запись | Пометить на экране можно, но запретить вторую запись экран не может — это в списке «Что на стороне экрана не решить» |
| **6** BOOK-04 после перезагрузки: `GET /api/holds/current` не отдает состав визита, цену и имя мастера | **Можно собрать из нескольких запросов:** черновик записи (услуги с количеством, «Любой мастер» или номер мастера, время, комментарий) хранить в `sessionStorage`. После перезагрузки: `GET /api/holds/current` — проверить, что бронь на то же время; `GET /api/masters?services=…` — имя мастера, цена и длительность визита; `GET /api/services` — названия и цены строк | Все, кроме состава визита, отдает API; состав знает только браузер. Нет черновика или бронь на другое время — вернуть на BOOK-03 |
| **7** AUTH-01, BOOK-03: плашка «Войдите, чтобы завершить запись. Выбранное время закреплено за вами» | **Значение брать из API, а текст на экране привести к нему:** «Войдите, чтобы закрепить время и завершить запись». После входа — `POST /api/holds`; если время заняли — BOOK-M1 с альтернативами | Гостю API бронь не создает, поэтому обещание «время закреплено» было бы неправдой |
| **8** AUTH-01: «Войти по коду из SMS» | **Убрать элемент из верстки** | SMS в проекте нет, вход только по паролю |

После нее клиент снова нажимает «Изменить» и получает новый код | Код действует 15 минут, и повторный запрос проще, чем хранить состояние, которого нет в API |
| **11.2** CAB-07: сохранить новый телефон сразу, без кода | **Убрать элемент из верстки:** телефон только для чтения, подсказка «Сменить номер можно через студию» | API меняет номер только по коду от администратора, а таких кодов по решению студии нет. Номер в карточке меняет администратор (`PATCH /api/admin/clients/:id`) |
| **11.3** CAB-07: одна кнопка «Сохранить» для имени, телефона и e-mail | **Убрать элемент из верстки:** общую кнопку заменяют «Сохранить» у имени (`PATCH /api/profile`) и «Изменить» у e-mail (код, AUTH-02) | У имени и e-mail разные пути сохранения: имя — сразу, e-mail — после кода |

## 2. Эндпоинты, которым не нашлось экрана

Варианты решения: экран будем верстать позже; добавить кнопку на существующий экран; добавить окно подтверждения; оставить как есть.

| Находка | Решение | Почему |
|---|---|---|
| **1** `PATCH /api/profile` с `marketingConsent` — подписаться на новости или отказаться после регистрации | **Добавить кнопку на существующий экран:** переключатель «Получать новости и акции» в CAB-07 | Согласие на новости добровольное, и отозвать его клиент должен сам, так же легко, как дал (152-ФЗ) |

| **8** `GET` и `PATCH /api/admin/settings` — контакты студии, правила записи и режим технических работ | **Экран сверстан:** A-26 «Настройки студии» (`/admin/settings`, `web/admin/settings.html`). В прототипе его нет: настройки меняются раз в несколько месяцев, и экран под них не рисовали, но без него нельзя выключить режим технических работ, с которым стартует новая база. ## Что на стороне экрана не решить

* Запрет второй записи клиента на то же время к другому мастеру: сервер его не проверяет, экран может только предупредить (список 1, пункт 5).
* Сохранение нового телефона клиентом без кода: API меняет номер только по коду от администратора (список 1, пункт 11.2).
* Удаление из API подтверждения телефона и кодов по звонку: `POST /api/profile/phone`, `/phone/confirm`, сброс пароля по коду, `POST /api/admin/users/:id/phone-code` и `/password-reset-code`, поле `phoneVerified`. Пока они есть, ими можно воспользоваться в обход экранов.
* Текст ответа API в сценарии 16 без e-mail в карточке: `message` по-прежнему обещает код от администратора (экран показывает свой текст, список 1, пункт 13.1).
* Отдача страницы интерфейса по пути `/reset-password` из письма: это настройка веб-сервера хостинга (список 1, пункт 10.2).
* Эндпоинт ближайшего свободного времени и дней со слотами за период: без него календарь и «Ближайшее: …» собираются десятками запросов (список 1, пункты 3 и 4).
* Документация и тесты под решение «телефон не подтверждается»: `docs/api.md`, `docs/db-schema.md`, тесты сервера.

* услуги: `GET /api/admin/services`, `POST /api/admin/services`, `PATCH /api/admin/services/:id`, `POST` и `PATCH /api/admin/service-categories` (название и порядок);
* фото работ: `GET /api/admin/photos`, `POST /api/admin/photos?bookingItemId=…`, `PATCH` и `DELETE /api/admin/photos/:id`.
