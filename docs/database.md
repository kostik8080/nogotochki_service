## 1. Как устроена база и как она связана с логикой проекта

### 1.1. Общие принципы

* **SQLite, один файл.** Путь задает `DATABASE_PATH`; при разработке — `server/data/nogotochki.db`. Режим WAL, `busy_timeout = 5000`, внешние ключи включаются при каждом подключении.
* **Таблицы `STRICT`.** SQLite без этого молча записал бы текст в числовое поле.
* **Время — текст ISO 8601 в UTC** с миллисекундами: `2026-09-24T07:00:00.000Z`. Строки одной длины сравниваются как время, на этом держатся индексы и проверки пересечений. Формат проверяет `CHECK ... GLOB` у каждого поля `*_at`. В часовой пояс студии (`settings.timezone`, `Europe/Moscow`) время переводится только при показе. Дата без времени — `YYYY-MM-DD`, время по часам студии — `HH:MM`, дни недели — ISO (1 — понедельник, 7 — воскресенье).
* **Деньги — целые копейки** (`*_kop`, с миграции 004; до нее — рубли `*_rub`), длительности — минуты (`*_min`), логические поля — `INTEGER` 0/1 с `CHECK`, наборы значений — английские коды в `CHECK`. Русские подписи есть только в интерфейсе.
* **Ничего важного не удаляется.** У всех внешних ключей `ON DELETE RESTRICT`. Записи, их состав и история защищены триггерами от удаления. Мастеров и услуги отключают (`is_active = 0`), аккаунт клиента обезличивают.
* **Бизнес-правила защищены на двух уровнях.** Сервер проверяет их в транзакции, а база повторяет самые опасные проверки триггерами. Даже ошибка в коде не создаст двойную запись.

### 1.3. Как ключевые правила паспорта выражены в базе

| Правило продукта | Как устроено в базе |
|---|---|
| Мастер не обслуживает двух клиентов одновременно (сценарий 4) | Триггеры `bookings_no_overlap_*` и `slot_holds_no_overlap` сравнивают промежутки `[starts_at, busy_until)` с учетом уборки. Исключение — осознанное наложение администратором (`bookings.is_overbooking`, сценарий 18 паспорта, миграция 005). Вторая линия защиты — частичный уникальный индекс `bookings (master_id, starts_at)` для действующих записей. Сервер создает бронь и запись в транзакции `BEGIN IMMEDIATE` (`transaction()` в `connection.ts`) |
| Свободное время показывается «вживую» | Слоты **нигде не хранятся**: их считают при запросе из режима студии, графика, изменений на дату, блокировок, записей и чужих действующих броней. Алгоритм — `db-schema.md`, раздел 7, реализация — `booking/slots.ts` (см. 1.6) |
| Время удерживается 10 минут | Строка `slot_holds` с `expires_at`. Одна бронь на пользователя (`owner_id UNIQUE`). Истекшая бронь просто перестает учитываться, удалять ее для корректности не нужно |
| Уборка между клиентами | `services.cleanup_min`. В записи — `busy_until = ends_at + наибольшая уборка` среди услуг, копируется на момент записи |
| Цена и длительность фиксируются в момент записи | `booking_items` копирует название услуги, цену за единицу, итоговую цену и длительность; `bookings.price_level` — уровень мастера, `busy_until` — уборка на момент записи. Сумма записи не хранится: это `SUM(booking_items.price_kop)`. Поэтому новая цена или длительность в справочнике (в том числе из админ-панели) действует только для новых записей, а созданные остаются прежними; пересчет бывает только один — при переносе к мастеру другого уровня (решение 11) |
| Полная история переносов и отмен | Перенос меняет ту же строку `bookings`, а старое время уходит в `booking_events`. Отмена хранится только событием `cancelled`: триггер не даст поставить статус отмены без него. `bookings.version` — защита от одновременного редактирования двумя сотрудниками |
| Записи не удаляются | Триггеры `*_no_delete` на `bookings`, `booking_items`, `booking_events` |
| Новый график с даты (сценарий 14) | `master_weekly_hours.valid_from` / `valid_to`, триггер запрещает пересечение периодов |
| Роли | Триггеры проверяют роль по каждой ссылке на `users` (раздел 10.8 схемы). Роль после создания не меняется. У администратора и мастера пароль обязателен |
| Пароли | Только хеш: `CHECK` пропускает argon2id, bcrypt и PBKDF2-SHA256 и отклоняет открытый текст. Сервер хеширует argon2id (`auth/password.ts`) |
| Роль «мастер» | Учетная запись в `users` (роль `master`), профиль мастера — в `masters`, связь — `masters.user_id` (уникальная, может быть `NULL`). Мастер только смотрит свое расписание (`GET /api/master/schedule`) и карточки записей из него, без цен и контактов клиентов; действовать за клиента или администратора и держать бронь не может |
| Новая база на проде закрыта для клиентов | Миграция 002 создает настройки с `is_maintenance = 1`: адрес и телефон в ней временные |

Коды ошибок, которыми база отклоняет изменения (`RAISE(ABORT, …)`). Сервер будет переводить их в сообщения для пользователя: `SLOT_TAKEN`, `BOOKING_DELETE_FORBIDDEN`, `CANCEL_EVENT_REQUIRED`, `SERVICES_INCOMPATIBLE`, `MASTER_CANNOT_DO_SERVICE`, `SCHEDULE_PERIOD_OVERLAP`, `WRONG_USER_ROLE`, `ROLE_IMMUTABLE`, `WRONG_SERVICE_KIND`. В `node:sqlite` код приходит в `error.message`, а `error.code` у всех одинаковый — `ERR_SQLITE_ERROR`.

### 1.6. Расчет свободных слотов

`server/src/booking/slots.ts` реализует раздел 7 схемы. Функции получают базу и параметры, ничего не пишут и не кэшируют:

| Функция | Что возвращает | Где понадобится |
|---|---|---|
| `getMasterDay(db, masterId, date)` | Режим дня по правилам 7.2: `open` с рабочим окном, `studio_closed` с причиной (или `null` в обычный выходной студии), `master_off`, `master_inactive` | Календарь записи, шахматка, график смен |
| `getFreeIntervals(db, q)` | Рабочее окно минус записи с уборкой, блокировки и чужие действующие брони | «Свободные часы» в шахматке, «ближайшие окна» в A-02 |
| `getSlots(db, q)` | Моменты начала визита длительностью D с уборкой C: `{ startsAt, endsAt, time }` | BOOK-03, CAB-04, A-02, A-04 |
| `getVisitTiming(db, serviceIds)` | D — сумма длительностей, C — наибольшая уборка | Перед `getSlots` |
| `findMastersForServices(db, serviceIds)` | Активные мастера, которые выполняют все услуги | BOOK-02 |
| `getSlotsAnyMaster(db, q)` | Слоты «Любой свободный мастер» со списком свободных мастеров в каждом | BOOK-02, BOOK-03 |

Параметры запроса `q`:
- `now` — текущий момент. Его передает вызывающий код: так расчет можно проверять на фиксированной дате.
- `audience` — `'client'` или `'admin'`. Минимальное время до визита и горизонт действуют только для клиента.
- `viewerId` — чья бронь не считается помехой, то есть бронь самого пользователя.
- `excludeBookingId` — переносимая запись, ее время не считается занятым.

Промежутки полуоткрытые, поэтому запись, которая заканчивается ровно в 12:00, не мешает слоту 12:00. Занятое время читается с запасом в 60 минут после конца окна (наибольшая уборка по `CHECK`): уборка нового визита может выйти за смену.

Чего расчет не делает — это задачи сервера при создании брони и записи:
- не проверяет режим технических работ;
- не проверяет совместимость услуг и правила опции;
- не помечает слоты «У вас запись в это время».

Итоговую защиту от занятого времени дают триггеры базы.

**Тесты расчета слотов** (`test/slots.test.ts`, 23 теста) строят базу в памяти на фиксированных датах 2026 года. Покрыты:
- все примеры раздела 7.4: обед Анны, личное время Марины, выходной Елены, 31 декабря, смена графика;
- порядок правил 7.2;
- уборка до следующей записи и стык записей;
- отмененные записи, неявки, перенос;
- свои, чужие и истекшие брони;
- визит из нескольких услуг в конце дня;
- 2 часа до визита и горизонт 90 дней;
- вариант «Любой мастер».

Что тесты ловят ошибки, проверено порчей кода: без проверки уборки, без броней и без правила «студия важнее мастера» падает соответствующий тест.

**Тесты API** (`test/api.test.ts`, 29 тестов; `test/api-extended.test.ts`, 22 теста — восстановление пароля, профиль и удаление аккаунта, статусы, баннер, расписание, клиентская база, фото, настройки; `test/mailer.test.ts`, 3 теста — SMTP-клиент против учебного сервера) поднимают сервер на свободном порту поверх базы в памяти с тестовыми данными и ходят в него через HTTP: регистрация и вход, блокировка после неверных паролей, цены в копейках, слоты по сценариям паспорта, бронь и конфликт двух клиентов, запись, перенос, отмена, правило 24 часов, истекшая бронь, права клиента и администратора, конфликт версий.

### 1.7. Как API работает с базой

* **Проверка данных до базы.** Каждый обработчик сначала разбирает тело и строку запроса (`http/validate.ts`): типы, форматы, обязательные поля, неизвестные поля. Только потом — запросы к базе.
* **Транзакции.** Бронь, запись, перенос и отмена идут в `transaction()` (`BEGIN IMMEDIATE`): сервер заново считает, свободно ли время (рабочие часы и блокировки триггеры не проверяют), и пишет в той же транзакции. Код триггера (`SLOT_TAKEN` и другие) API переводит в ответ 409.
* **Один путь записи** (`booking/booking-service.ts`). Создание, перенос, отмену и итог визита выполняют функции `createBooking`, `rescheduleBooking`, `cancelBooking`, `setVisitResult` — одни для клиента, мастера и администратора; права ролей проверяются в них, а не в маршрутах API. Строки пишут только `insertBookingRows`, `writeReschedule`, `writeCancellation`, `writeStatusChange`; ими же пользуются удаление аккаунта и тестовые данные. Тест `booking-service.test.ts` ищет в `src/` и `scripts/` запись в эти таблицы мимо сервиса и падает, если найдет. Тесты базы (`slots.test.ts`, `overlap.test.ts`) вставляют строки напрямую намеренно: они проверяют триггеры без сервера.
* **Вложенные транзакции.** `transaction()` внутри открытой транзакции работает через `SAVEPOINT`: так удаление аккаунта вызывает ту же `cancelBooking`, а ошибка откатывает только вложенную часть.
* **Защита от двойной записи — три уровня** (тесты — `test/overlap.test.ts`). 1) Сервер заново считает свободное время внутри транзакции. 2) Транзакция начинается с `BEGIN IMMEDIATE`: блокировка на запись берется сразу, поэтому второй одновременный запрос ждет (`busy_timeout`), а затем видит уже созданную запись. С обычным `BEGIN` (DEFERRED) оба запроса прочитали бы «свободно», а второй упал бы на «database is locked» при попытке писать по устаревшему снимку. 3) Триггеры `bookings_no_overlap_insert` / `_update` и `slot_holds_no_overlap` отклоняют пересечение `[starts_at, busy_until)` одного мастера кодом `SLOT_TAKEN`; отмененные записи не участвуют, стык не пересечение. Вторая линия — частичный уникальный индекс `bookings (master_id, starts_at)`. Любой из этих отказов API превращает в 409 с ближайшими свободными слотами (`booking/availability.ts`: `isSlotConflict`, `nearestFreeSlots`); альтернативы подбираются после отката транзакции.
* **Порядок отмены.** Сначала событие `cancelled` в `booking_events`, затем статус — иначе триггер 10.7 отклонит смену статуса.
* **Своя бронь снимается до вставки записи**: триггер записи учитывает любые действующие брони.
* **Версия записи.** Перенос и отмена обновляют строку условием `WHERE id = ? AND version = ?`; 0 измененных строк — ответ 409 `VERSION_CONFLICT`.
* **Роли и права.** В базе у учетной записи одна роль (`users.role`, не меняется после создания), а в коде роли — список: сессия дает `SessionUser.roles`, `GET /api/auth/me` — `roles`. Права проверяет только `hasRole` (`auth/sessions.ts`) — наличие роли в списке, а не равенство. Раздел администратора закрывает одна функция `requireAdmin` (`api/guards.ts`): `app.ts` вызывает ее для всех `/api/admin/*` до поиска маршрута, и через нее же проходят страницы `/admin`, которые сервер отдает сам (`web/admin-pages.ts`: гостю — вход, клиенту и мастеру — 403). Обработчики раздела роль не проверяют — новый эндпоинт защищен сам. Поля `role` и `roles` API не принимает: роль назначается только в базе.
* **Ответы собираются явно** (`api/views.ts`): строки базы целиком наружу не уходят, хеши паролей и токенов не возвращаются, контакты клиента видит только администратор.
* **Уборка.** Сервер раз в минуту удаляет истекшие брони и закрытые или истекшие сессии (`booking/cleanup.ts`); истекшие брони удаляются и при каждой новой брони.
* **Коды** (`auth/codes.ts`). В `auth_codes` — только хеш: у кода из 6 цифр — SHA-256 от номера пользователя, цели и кода, у токена ссылки — от 32 случайных байт. Новый код гасит прежние той же цели (`consumed_at`), неверная попытка увеличивает `attempts` отдельной транзакцией — откат ошибки ее не стирает. Новый e-mail или телефон до ввода кода лежит только в `auth_codes.target`.
* **Удаление аккаунта** — обезличивание по решению 20: строка `users` остается с именем «Удаленный клиент» и пустыми контактами, паролем и согласиями, `deleted_at` заполнено. Удаляются `client_profiles`, `client_notes`, `auth_codes`, `sessions`, `slot_holds` клиента и неопубликованные фото его визитов (строки, затем файлы — после фиксации транзакции). Предстоящие записи отменяются событием `cancelled`, комментарии к записям стираются.
* **Предпросмотр изменений расписания.** `applyOrPreview` (`booking/affected.ts`) выполняет изменение в транзакции и с `dryRun` откатывает ее: список задетых записей считается тем же кодом, что и после сохранения.
* **Фото.** Файл пишется до вставки строки; если вставка упала, файл удаляется. Путь из базы разрешается только внутри `UPLOADS_DIR`.

### 1.8. Действия администратора с записью клиента и что после них видит клиент

Записи ведет администратор, а клиент видит результат в кабинете. Здесь собрано, что администратор может
сделать с чужой записью (страница «Записи», `/admin`) и что после каждого действия появляется у клиента.
Уведомление — сообщение в колокольчике из таблицы `notifications` (раздел 5.23), баннер — плашка «Студия
отменила / перенесла запись» на «Моих записях» и в карточке записи (`bookings.client_acknowledged_at`).

| Действие администратора | Что происходит в базе | Что видит клиент |
|---|---|---|
| **Создать запись за клиента** (`POST /api/bookings` с `clientId` или `newClient`) | Новая строка `bookings` со статусом `active`; бронь администратору не нужна | Запись появляется в «Моих записях» как активная. Уведомления нет: о визите клиент договорился со студией сам — по телефону. Напоминания о визите (за сутки, 2 часа, 15 минут) придут как обычно |
| **Перенести** (`POST /api/bookings/:id/reschedule`) | Меняется время (и мастер) **той же** строки, новая запись не создается; старое и новое время, мастер, суммы и причина — в `booking_events` | Уведомление «Запись «…» на четверг, 15 октября, 10:00 перенесена студией на пятницу, 16 октября, 11:00» и баннер «Студия перенесла запись». В карточке — новое время. Запись одна: двух сообщений подряд («отменена» и «создана») клиент не получает |
| **Отменить от имени студии** (`cancel` с `by: 'studio'`) | Событие `cancelled` в журнале, затем статус `cancelled_by_studio`; строка не удаляется, время мастера освобождается сразу | Уведомление «Запись «…» на четверг, 8 октября, 10:00 отменена студией. Причина: …» и баннер. Запись уходит из предстоящих в «Историю» со статусом «Отменена студией», в карточке — причина и кнопка «Выбрать новое время» |
| **Отменить по просьбе клиента** (`cancel` с `by: 'client'`) | То же, но статус `cancelled_by_client` | В истории — «Отменена вами», в карточке «Вы отменили запись. Причина: …». Уведомление и баннер все равно приходят и говорят «студия отменила»: действие внес сотрудник, а не клиент (расхождение в тексте, решение не принято) |
| **Визит завершен** (`status` = `completed`) | Событие `status_changed`, статус `completed` | Запись в «Истории» со статусом «Завершена» и кнопкой «Повторить». Уведомления нет: клиент только что был в студии |
| **Клиент не пришел** (`status` = `no_show`) | Событие `status_changed`, статус `no_show` | Запись в «Истории» со статусом «Клиент не пришел». Уведомления нет. Отметка влияет на метки клиента в клиентской базе |
| **Записать поверх занятого времени** (`isOverbooking: true`) | Новая запись с `is_overbooking = 1`; проверка занятости не отключается — наложение разрешает пересечение только с записями и блокировками, но не с рабочим временем и чужими бронями | Тот, чье время заняли вторым визитом, получает уведомление «На время вашей записи «…» студия назначила еще один визит». Его запись не меняется. Новый клиент видит обычную активную запись: отметка наложения ему не показывается |
| **Заблокировать время мастера** (`POST /api/admin/time-blocks`) | Строка `time_blocks`: обед, личное время, выходной, отпуск, больничный. Созданные записи база не трогает — их администратор разбирает сам | Уведомления нет: записи клиента не изменились. Заблокированное время перестает показываться свободным при новой записи и при переносе |
| **Одобрить заявку мастера** (`POST /api/admin/requests/:id/approve`) | Отпуск, отгул и больничный создают блокировку времени, новый график — строки `master_weekly_hours` с даты. Записи под изменением база не трогает | Клиенту уведомления нет: его записи не изменились. Время мастера пропадает из свободного. Мастер видит в своих заявках, что она одобрена |

Правило для уведомлений одно: они создаются, только если запись изменил **не ее владелец**. Поэтому свои
действия клиента — запись, перенос, отмена, в том числе отмена предстоящих записей при удалении аккаунта —
уведомлений не создают.

### 1.9. Уведомления: какие события и что проверено

Событий три, других пока нет (решение владельца студии от 30.09.2026). Все три создаются в
`server/src/notify/notifications.ts`, вызовы — в `server/src/booking/booking-service.ts`.

| Событие (`event_type`) | Когда создается | Кто получает | Пример текста |
|---|---|---|---|
| `booking_cancelled` | `cancelBooking` — администратор отменил чужую запись | владелец записи | «Запись «Маникюр без покрытия» на четверг, 8 октября, 10:00 отменена студией. Причина: Заболел мастер.» |
| `booking_rescheduled` | `rescheduleBooking` — администратор перенес чужую запись | владелец записи | «Запись «Маникюр без покрытия» на четверг, 15 октября, 10:00 перенесена студией на пятницу, 16 октября, 11:00.» При смене мастера добавляется «Визит проведет Елена Смирнова.» |
| `booking_overbooked` | `createBooking` и `rescheduleBooking` с `isOverbooking` — администратор занял время вторым визитом | владельцы записей, чье время теперь делится (не тот, кого записали) | «На время вашей записи «Маникюр без покрытия» — пятница, 16 октября, 11:00 — студия назначила еще один визит: мастер Анна Ковалева примет двух клиентов. Ваша запись сохранена, время не изменилось.» |

Текст пишется при создании и не меняется: он описывает событие так, как оно выглядело тогда. Общих фраз
вроде «ваша запись изменена» в нем нет — всегда конкретные дата и время в часовом поясе студии. День недели
ставится в нужный падеж («перенесена на пятницу»); имя мастера не склоняется, поэтому фразы построены так,
чтобы оно стояло в именительном падеже.

**Что проверено** (`server/test/notifications.test.ts`, 8 проверок, и ручная проверка в браузере 30.09.2026):

| Сценарий | Ожидание |
|---|---|
| Администратор отменил запись клиента | Уведомление `booking_cancelled` с датой, временем и причиной; ссылка ведет на эту запись |
| Администратор перенес запись | `booking_rescheduled` со старым и новым временем; при смене мастера — его имя |
| Администратор записал второго клиента на то же время | `booking_overbooked` приходит владельцу прежней записи и ссылается на **его** запись, а не на чужую |
| Администратор создал запись за клиента | Уведомления нет |
| Клиент сам записался, перенес и отменил визит | Уведомлений нет ни одного |
| Список и счетчик | `GET /api/notifications` отдает `unreadCount` вместе со списком; после «прочитано» счетчик уменьшается в том же ответе; повторное «прочитано» ничего не меняет |

### 1.10. Заявки мастера: кто что может и что проверено

Решение заказчика от 30.09.2026: мастер сам просит отпуск или другой график, а администратор решает.
Паспорт дополнен — функция 2 мастера и функция 11 администратора. Записи мастер по-прежнему не ведет.

| Кто | Что может | Чего не может |
|---|---|---|
| Мастер | Подать заявку за себя: отпуск, отгул, больничный, новый график с даты, свободная просьба словами. Видеть свои заявки и решение с причиной. Отозвать заявку, пока она на рассмотрении | Подать заявку за другого мастера (номер мастера берется из его профиля, поле из запроса не принимается), изменить расписание сам, увидеть чужие заявки, рассмотреть свою |
| Администратор | Видеть все заявки и число нерассмотренных, посмотреть записи, которые заденет одобрение, одобрить (заявка применяется сразу) и отклонить с причиной | Рассмотреть заявку второй раз: решенную заявку триггер `master_requests_decided_final` больше не меняет, поэтому одобрение не применится дважды |
| Клиент | — | Заявки ему недоступны: `/api/master/*` отвечают 403, раздел `/master` — страницей отказа |

## 2. Сложности и как мы их решили

| # | Проблема | Решение |
|---|---|---|
| 1 | В SQLite нет ограничения `EXCLUDE`, как в PostgreSQL, чтобы запретить пересечение записей | Триггеры на вставку и изменение плюс частичный уникальный индекс как вторая линия защиты. Одновременность обеспечивает `BEGIN IMMEDIATE`: писать в SQLite может только одна транзакция |
| 2 | У поля `email` сравнение без учета регистра (`COLLATE NOCASE`), поэтому проверка `email = lower(email)` всегда была истинной | В проверке явно указано побайтовое сравнение: `email = lower(email) COLLATE BINARY` |
| 3 | В триггере `BEFORE INSERT` значение `NEW.id` еще не присвоено, и сравнение `<>` с ним отбросило бы все строки | Используется `IS NOT` вместо `<>` |
| 4 | Git в Windows заменяет окончания строк, и контрольная сумма миграции «менялась» без правок | Сумма считается по тексту с окончаниями строк `\n`; `.gitattributes` хранит `*.sql` с LF, а с 27.09.2026 — все текстовые файлы с LF и в репозитории, и в рабочей папке при любой настройке `core.autocrlf`; двоичные файлы помечены `binary` |
| 5 | `better-sqlite3` — нативный модуль. После разрешения скриптов установки `npm ci` падал на `node-gyp rebuild`: нет компилятора C++ | Перешли на встроенный `node:sqlite` (раздел 3), нативных зависимостей не осталось |
| 6 | На проде зависимости ставят без dev-пакетов, и команды через `tsx` не запустились бы; `tsc` не копирует `.sql` | `npm run build` собирает `dist/` и копирует миграции; на проде — команды `prod:*` на чистом Node |
| 7 | После сборки код лежит в `dist/src/`, и путь «на уровень выше» больше не указывает на `server/` | `config.ts` ищет папку сервера по ближайшему `package.json` |
| 8 | База внутри папки с кодом пропала бы при обновлении | В production `DATABASE_PATH` и `BACKUP_DIR` обязательны, абсолютные и вне папки с кодом, иначе команды не запускаются. В Windows `path.relative` между дисками возвращает абсолютный путь — это учтено |
| 9 | Без строки `settings` пустая база на проде не посчитает ни одного слота, а тестовые данные туда не загружаются | Миграция 002 создает настройки; режим технических работ включен, пока не введены настоящие контакты |
| 10 | Простое копирование файла базы в режиме WAL может дать битую копию | `VACUUM INTO`: целостный снимок без остановки сервера. Копия проверяется `integrity_check` и переводится в один файл (`journal_mode = DELETE`) |
| 11 | Роль `master` требовала изменить `CHECK`, а в SQLite это делается только пересозданием таблицы. На `users` ссылаются почти все таблицы. Внутри транзакции `PRAGMA foreign_keys` не действует, а с `defer_foreign_keys` коммит падал: удаление старой таблицы оставляло счетчик нарушений. Переименование новой таблицы отказывалось работать, пока триггеры ссылаются на удаленную `users` | Пометка `-- migrator: foreign_keys=off` в первой строке миграции. Мигратор выключает внешние ключи до транзакции, перед коммитом проверяет все ссылки (`foreign_key_check`), потом включает их обратно. Для переименования миграция включает `legacy_alter_table`. Триггеры на самой пересоздаваемой таблице удаляются вместе с ней, их нужно создать заново |
| 12 | Повторяемые тестовые данные: `INSERT OR IGNORE` не подошел — триггеры `BEFORE INSERT` срабатывают раньше проверки уникальности и отклоняют повтор ошибкой | Сначала поиск строки по ключу, вставка — только если ее нет (`ensure()` в `dev-seed.ts`) |
| 13 | Тестовые данные привязаны к «сегодня»: повторный запуск в другой день сдвинул бы отпуск и записи и наложил бы их на старые | Сценарные данные добавляются один раз, пока у тестовой клиентки нет записей. Регулярные блокировки дополняются на новые даты без дублей |
| 14 | Переход с рублей на копейки: поля денег участвуют в `CHECK` (`price_kop = unit_price_kop * quantity`, цена топ-мастера не ниже цены мастера), а менять `CHECK` в SQLite можно только пересозданием таблицы | `ALTER TABLE … RENAME COLUMN` (SQLite 3.25+) сам переписывает имя поля в `CHECK`, индексах и триггерах. Обе цены меняются одним `UPDATE`, поэтому `CHECK` видит уже согласованную пару. Пересоздавать таблицы не понадобилось |
| 15 | `COLLATE NOCASE` в SQLite не различает регистр только латинских букв. Для `services.name` и `service_categories.name` «Маникюр» и «маникюр» — разные значения, и `UNIQUE` пропустит дубль с другим регистром кириллицы | API сравнивает названия услуг без учета регистра сам (`toLocaleLowerCase('ru')`) перед сохранением. Для e-mail правило работает: адреса латинские и хранятся в нижнем регистре. Схема не менялась |

## 3. Драйвер SQLite: `node:sqlite`

Используется **встроенный модуль Node.js `node:sqlite`**, класс `DatabaseSync`. Сторонних драйверов нет, и у серверной сборки вообще нет зависимостей для работы: в `package.json` только dev-пакеты (`typescript`, `tsx`, `@types/node`).

**Почему он:**

* **Хостинг — BeGet, окружение заранее неизвестно.** Нативный модуль (`better-sqlite3`) нужно либо скачать готовым под платформу, либо скомпилировать. На хостинге без компилятора C++ установка падает — мы это воспроизвели. Встроенному модулю нужен только сам Node.js.
* **Синхронный API** подходит для SQLite: запросы идут в том же потоке, а транзакция `BEGIN IMMEDIATE` … `COMMIT` не прерывается чужим кодом между проверкой «свободно ли время» и вставкой.
* **Свежая SQLite внутри Node** (в Node 24.19 — 3.53) с поддержкой `STRICT` и всего, что использует схема.

**История выбора.** Сначала был `better-sqlite3` — зрелая библиотека с удобным API. Под Windows он работал из готовых бинарных файлов. Но когда мы разрешили его скрипт установки, npm запустил сборку из исходников, и чистая установка упала. На `node:sqlite` перешли, когда стало ясно, что версия Node на BeGet неизвестна.

**Отличия API, которые важно помнить:**

| `node:sqlite` | Что делать |
|---|---|
| Нет встроенного хелпера транзакций | `transaction(db, fn)` из `connection.ts`: `BEGIN IMMEDIATE`, откат при ошибке |
| Нет `db.pragma()` и `.pluck()` | `db.exec('PRAGMA …')`, `db.prepare('PRAGMA …').get()`, выбирать поле из объекта |
| `undefined` нельзя передать в параметр | Передавать `null` |
| Лишний именованный параметр — ошибка | Передавать ровно те ключи, что есть в запросе |
| Строки результата — объекты без прототипа, `all()` типизирован как `Record<string, SQLOutputValue>[]` | Приводить через `as unknown as MyRow[]` |
| Внешние ключи включены по умолчанию | Все равно включаем явно в `openDatabase()` и проверяем |
| Ошибка SQLite: `error.code = 'ERR_SQLITE_ERROR'`, текст — в `error.message`, код SQLite — в `error.errcode` | Код `RAISE` из триггера (например, `SLOT_TAKEN`) читать из `message` |

## 4. Версия Node.js: 24.7 или новее

В `server/package.json` указано `"engines": { "node": ">=24.7" }`. Рекомендуется **последняя 24.x** — ветка с долгосрочной поддержкой (LTS). Проект проверен на **Node 24.19.0**; на других версиях не запускался.

**Откуда 24.7.** Требование складывается из возможностей Node, которыми пользуется проект. Версии сверены с документацией Node.js 26.09.2026:

| Что нужно проекту | С какой версии Node | Где используется |
|---|---|---|
| Модуль `node:sqlite` | 22.5, но только с флагом `--experimental-sqlite` | Вся работа с базой |
| `node:sqlite` без флага | 22.13 и 23.4 | То же |
| Опция `readOnly` у `DatabaseSync` | 22.12 | Проверка резервной копии, служебные проверки |
| Свойство `db.isTransaction` | 22.16 и 24.0 | `transaction()` в `connection.ts`: откат только открытой транзакции |
| **Минимум для `node:sqlite` в нашем коде** | **22.16 (ветка 22) или 24.0** | |
| `argon2` в `node:crypto` | **24.7.0** | Хеширование паролей argon2id (`auth/password.ts`), как требует паспорт |

Итоговый минимум проекта — **24.7**: его диктует argon2, а требования `node:sqlite` при этом выполняются. Опустить `engines` до 22.16 нельзя: на 22.x встроенного argon2 нет, и не запустятся `admin:create` и `db:seed`. Статус `node:sqlite` в документации Node — Stability 1.2, «кандидат в релиз»: API уже стабилизируют, но формально модуль еще экспериментальный. Поэтому при переходе на новую основную версию Node стоит прогнать `npm test` и `npm run db:check-schema`.

**Как проект защищен от неподходящей версии.** Проверок две, обе берут требуемую версию из `engines` в `package.json`:

1. **При установке.** `server/.npmrc` содержит `engine-strict=true`: `npm ci` и `npm install` на неподходящем Node останавливаются с ошибкой `EBADENGINE` и ничего не ставят. Это срабатывает при первой же выкладке, до сборки и миграций.
2. **При запуске команды.** Все `npm run …` запускаются с `--import ./scripts/node-version.mjs`. Этот модуль Node выполняет раньше основного кода и при старой версии пишет: «Нужен Node.js 24.7.0 или новее, установлен v…», путь к запущенному `node` и ссылку на этот раздел, а затем завершает команду с кодом 1. Проверка не может жить внутри самих команд: Node связывает все импорты до выполнения кода, и на старой версии команда упала бы раньше на `import { argon2Sync }` или `node:sqlite` с непонятной ошибкой. При запуске напрямую, без `npm run` (например, из CRON), флаг `--import ./scripts/node-version.mjs` указывается явно.

Обе проверки испытаны имитацией: во временной копии проекта в `engines` ставилась версия выше установленной. Настоящий старый Node не запускался. Без этих проверок на старом Node команды, которые хешируют пароли (`admin:create`, `db:seed`), падали бы на отсутствующем `argon2Sync`, а ниже 22.13 не открылась бы и сама база. В ранних выпусках 24.x при запуске может печататься `ExperimentalWarning` про SQLite. Это предупреждение, а не ошибка; в 24.19 его нет.

**Чек-лист для BeGet:**

1. `node -v` на сервере. Если ниже 24.7 — поставить последнюю 24.x до выкладки. Ветка 22.x не подойдет, даже свежая: в ней нет встроенного argon2.
2. `which node` — полный путь к нужному Node. Именно он указывается в задании CRON для резервных копий вместе с `--import ./scripts/node-version.mjs`: у cron свой, урезанный `PATH`, и там может оказаться другая версия.
3. После выкладки — `npm run prod:migrate`. Если команда отработала, Node и база в порядке.

## Правила изменений

Для людей и ИИ-ассистентов, которые меняют базу.

1. **Структура меняется только новой миграцией** `server/src/db/migrations/NNN_description.sql` со следующим номером. Примененные миграции не правятся: мигратор это заметит.
2. **В том же коммите обновляется [`docs/db-schema.md`](db-schema.md)**: описание поля или таблицы, ограничения, индексы (разделы 9 и 10.1), триггеры, номер версии и строка «Изменения версии N». Затем — `npm run db:check-schema`. Команда сверяет таблицы, поля, типы, обязательность, ключи, индексы, а также `CHECK`, `DEFAULT` и `COLLATE NOCASE` из описаний полей и строк «Проверка» раздела 5 с документом и должна пройти без расхождений. Проверку `CHECK` пишите в описании поля так же, как в миграции, — команда ищет ее текст в определении таблицы. Общие проверки (формат времени, логические поля, непустой текст) описаны в разделах 1–2 один раз и у каждого поля не повторяются.
3. **Изменить `CHECK`, внешний ключ или тип поля** можно только пересозданием таблицы. Такая миграция начинается строкой `-- migrator: foreign_keys=off`, а переименование в ней обрамляется `PRAGMA legacy_alter_table = ON/OFF`. Триггеры на самой пересоздаваемой таблице нужно создать заново. Образец — `003_master_role.sql`.
4. **Миграция с данными должна работать и на пустой базе, и на базе с данными.** Например, `INSERT OR IGNORE` в 002 не ломает базу, в которой строки уже есть.
5. **Тестовые данные поддерживаются вместе со схемой** и остаются повторяемыми: новая строка — через `ensure()` с ключом. После изменений: `npm run db:reset`, затем повторный `npm run db:seed` — второй запуск должен показать 0 добавленных строк.
6. **Время** — только `new Date().toISOString()` или `strftime('%Y-%m-%dT%H:%M:%fZ', 'now')`, в UTC.
7. **Пароли, коды и токены** — только хеши. Пароль хешируется `hashPassword()` из `auth/password.ts`.
8. **Запись, которая зависит от проверки** («свободно ли время», «есть ли событие отмены»), выполняется внутри `transaction()`.
9. **Если решение из этого документа меняется**, документ исправляется в том же коммите, а в журнал добавляется строка.

## Открытые вопросы

* **SQLite или PostgreSQL в production.** Паспорт называет PostgreSQL, сейчас все построено на SQLite. Для одной студии на VPS SQLite достаточно. Если переезд нужен, лучше сделать его до первых реальных данных (`db-schema.md`, спорное решение 1).
* **Права роли «мастер».** Мастер видит только свое расписание (`GET /api/master/schedule`); создание, перенос и отмена записи отвечают ему 403. Расширять права — вместе с интерфейсом мастера.
* **SMS не будет** (решение студии, схема версии 15). Коды приходят на e-mail, телефон подтверждает администратор, диктуя код по звонку. Риск — выдача кода постороннему; меры описаны в паспорте.
* **Конец визита в проверке пересечений — конец уборки** (`busy_until`, решение 32). Поэтому визиты 15:00–16:00 и 16:00–17:00 стоят вплотную, только если у первой услуги нет уборки. Если студия решит считать по `ends_at`, это новая миграция триггеров.
* **Копия базы вне сервера** пока делается вручную: копии в `BACKUP_DIR` лежат на том же сервере.
* **Версия Node на BeGet** неизвестна: проверить до первой выкладки (раздел 4).
* **Скрытый ввод пароля в `admin:create`** проверен только через поток ввода, в настоящем терминале — нет.
* **Вход через Яндекс работает на заглушке.** Приложение в Яндексе не зарегистрировано: сервис не опубликован, и постоянного адреса для возврата у него нет. **Перед публикацией заглушку нужно отключить** (`YANDEX_LOGIN_STUB` — пусто или 0) и подставить настоящий обмен кода на профиль в `fetchYandexProfile` (`server/src/auth/yandex.ts`). Заглушка пускает в аккаунт по нажатию кнопки, без проверки человека, поэтому на сервере в интернете она недопустима; запуск с `NODE_ENV=production` и `YANDEX_LOGIN_STUB=1` сервер отклоняет сам (`checkProductionConfig` в `src/config.ts`), но полагаться только на эту проверку не стоит.
* **Отправка писем со ссылками с личного ящика Яндекса не проходит.** Проверено 01.10.2026: тот же текст на свой ящик уходит, а на чужой — `554 5.7.1 Message rejected under suspicion of SPAM`; без ссылки уходит и на чужой. То есть письма со ссылкой сброса пароля с личного ящика не доставляются. Для разработки письма печатаются в консоль (не задан `SMTP_HOST`), для публикации нужен отправитель на своем домене с SPF, DKIM и DMARC.
